# openage technical feasibility investigation

- **Investigation date:** 2026-10-13
- **Source inspected:** [SFTtech/openage at `3da21ab486154432a459db1a10534cc0e344db95`](https://github.com/SFTtech/openage/tree/3da21ab486154432a459db1a10534cc0e344db95), committed 2026-10-03.
- **Verdict:** openage is a valuable RTS reference, but is not a ready foundation for Battle for La Roma's first playable slice.

This is a source inspection plus a local build attempt, **not a successful runtime test**. “Implemented” below means an execution path exists in source; it does not mean it worked here. “Defined” means data schema or conversion code exists without a matching live game system.

## Architecture and implementation status

The engine combines a C++20 `libopenage` core, Python package and asset converter, Cython glue, CMake code generation, Qt interface, graphics backends, and [nyan](https://github.com/SFTtech/nyan) content data. [`Engine`](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/libopenage/engine/engine.cpp) starts a time loop, game simulation, and optional presenter. The simulation owns an event loop, entity/terrain factories, and mod manager; rendering is attached through factories after game state creation. The repository [README](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/README.md) itself says gameplay is “basically non-functional.”

There may be experimental code elsewhere; no evidence here justifies treating it as player-ready functionality.

## Build and launch verification

Environment: macOS 27.0.1, Apple Silicon ARM64, Apple Clang 21, CMake 3.31.5, Ninja 1.11.1, Python 3.14.7. The clone and build files were kept under `/private/tmp`; upstream source was not edited.

1. `git clone --depth 1 https://github.com/SFTtech/openage.git /private/tmp/aomx-openage-investigation` succeeded at the commit above.
2. `cmake -S . -B /private/tmp/aomx-openage-build -G Ninja -DDOWNLOAD_NYAN=OFF` failed while checking Python because Cython was absent.
3. `UV_CACHE_DIR=/private/tmp/aomx-uv-cache uv sync --python /opt/homebrew/bin/python3.14` installed the packages pinned by upstream's `uv.lock` into its temporary `.venv`. A sandboxed first attempt failed initializing the default cache; the temporary cache workaround succeeded.
4. Retrying CMake with `-DPython3_EXECUTABLE=/private/tmp/aomx-openage-investigation/.venv/bin/python` passed Python/Cython checks, then failed because `toml11Config.cmake` was not found. Missing optional Doxygen produced only a warning.
5. `cmake --build /private/tmp/aomx-openage-build --parallel 4` failed with `build.ninja: No such file or directory`. `bin/run` was absent, so launch and tests could not be run.

Upstream's [dependency list](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/doc/building.md) additionally requires nyan, Qt6 Core/Quick/QuickControls/Multimedia, libepoxy, libpng, Eigen, FreeType, Fontconfig, HarfBuzz, Opus/Opusfile/Ogg, and graphics support; the [macOS guide](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/doc/build_instructions/macos.md) gives package and `--download-nyan` instructions. Several of those C++ packages are not installed here. Since configure failed before checking all of them, this is the first blocker, not a complete dependency failure list. A clean retry would install the guide's packages, use the pinned Python environment, configure with `-DDOWNLOAD_NYAN=YES`, build, run `make test`, then run `bin/run test`/`bin/run game` with an asset pack. That retry has not been performed.

## Fully original content and proprietary assets

The [README](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/README.md) says ordinary play uses original AoE assets that openage does not ship. The [run guide](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/doc/running.md) says `game` prompts for conversion when no converted modpack exists. The repository has test textures and a nyan test object, but no complete standalone game pack. Therefore a proprietary-free Battle for La Roma is **plausible in the content model, not verified as a runnable path**.

The [modpack format](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/doc/media/openage/modpacks.md) accepts nyan data, graphics, audio, scripts and translations, with `modpack.toml` for load order/dependencies. [`Game::load_data`](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/libopenage/gamestate/game.cpp) loads `.nyan` files from active packs. Original sprites and terrain can use [texture/sprite/terrain metadata parsers](https://github.com/SFTtech/openage/tree/3da21ab486154432a459db1a10534cc0e344db95/libopenage/renderer/resources/parser). The converter, however, is organized around known AoE/Genie formats, so authoring entirely new content needs a separate exporter or hand-authored metadata. The [API exporter](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/doc/running.md) is described as temporary, with API objects hardcoded in the converter.

| Original content | Likely route | Remaining engine work |
| --- | --- | --- |
| Civilizations and technologies | Define nyan player setups, entity variants, and patches in an original modpack. | Faction setup, research actions, tech application and UI. |
| Units and buildings | Define nyan entities/abilities and original sprites; load via modpack. | Spawn selection without hardcoded AoE test IDs, production, placement, construction, combat. |
| Terrain and maps | Author texture/terrain metadata and nyan terrain types. | Replace fixed test chunks with a map format and loader; test collision/path costs. |
| Resources | Define nyan resource types and costs. | Implement stockpile, gathering, transport, spend rules, and tests. |
| Interface | Qt/QML and renderer HUD assets. | Build Battle for La Roma menus, HUD, localization, accessibility and input flows. |

No proprietary AoE files should be copied, converted into the product, or made a runtime requirement. A minimal original-content boot test would need to prove an `engine` API pack plus an independent Battle for La Roma pack can start from a fresh asset directory. This is an unresolved gate. openage code is [GPLv3 or later](https://github.com/SFTtech/openage/blob/3da21ab486154432a459db1a10534cc0e344db95/copying.md); distribution implications need review before selecting it. The project's own license is undecided.

## Risks and next evidence

The largest risk is scope: implementing the missing economy, construction, combat, technology, maps, AI and multiplayer inside openage is engine development before game validation. The next useful openage experiment, if reconsidered, is a clean build plus original asset-only boot, then one native gather/build vertical slice. None of those outcomes are presently verified. See [engine comparison](engine-comparison.md), [prototype plan](prototype-plan.md), and [decision 001](architecture-decisions/001-engine-selection.md).
