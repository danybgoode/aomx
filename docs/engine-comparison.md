# Engine comparison: openage and Godot

**Basis:** openage source at [`3da21ab`](https://github.com/SFTtech/openage/tree/3da21ab486154432a459db1a10534cc0e344db95) and the [local investigation](technical-feasibility.md); Godot capabilities from current official documentation. No Godot prototype or benchmark was run. Estimates are engineering judgments, not measured schedules.

| Criterion | openage | Godot 4.x stable |
| --- | --- | --- |
| Initial implementation | C++/Python/Cython/nyan/Qt toolchain, then fill large RTS gameplay gaps. The local CMake build stopped at a missing C++ dependency. | Install editor and start a text-based project. Must write RTS rules from scratch, but scene/UI/asset tooling already exists. |
| First playable slice | Longer and uncertain: source has movement demo, but no gathering or construction system, with fixed test map/content assumptions. | Likely shorter: [isometric TileSet/TileMapLayer](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html), input, UI and scripts can deliver a small slice without engine changes. This is a proposal, not a measured result. |
| RTS simulation | Event loop, entity components, pathfinding and nyan API are promising. Complete economy/combat/AI loops are absent. | No built-in AoE-style economy/combat framework. A deliberately separate simulation module must implement all game rules. |
| Rendering | Purpose-built terrain/world/HUD stages and sprite metadata; game rendering unverified locally. | Mature 2D canvas, sprites, shaders, UI and isometric tile layouts. [TileSet documentation](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html) confirms isometric shape support. |
| Pathfinding | Sector/portal/flow-field code exists; dynamic RTS load is unbenchmarked. | [AStarGrid2D and NavigationServer2D](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_introduction_2d.html) exist. Crowd scale, frequent obstacle changes and avoidance need custom policy and benchmarks; [navigation guidance](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_optimizing_performance.html) warns against excessive replans. |
| Determinism | Event scheduling and some fixed-point utilities exist, but there is no demonstrated deterministic complete match or network sync. | [Godot physics is not deterministic](https://docs.godotengine.org/en/stable/tutorials/physics/physics_introduction.html). Keep authoritative rules in fixed-tick, integer/fixed-point code with seeded RNG and stable iteration order; do not depend on physics for match outcomes. |
| Multiplayer | README goal; no validated game network loop found. | [High-level multiplayer/ENet](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html) and [headless server](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html) supported. Server authority, synchronization, reconnects and anti-cheat are still game work. |
| Modding | Nyan inheritance/patches and modpack loader are strong concepts; standalone original game workflow unproven. | Text/serialized resources and PCKs support data packs, but schema, validation, dependency handling and safe loading must be designed by us. |
| Automated testing | C++/Python tests and demos registered; build is prerequisite. No full game behavior suite. | [Headless command line](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html) supports script/scenes and CI. Pure rules can have deterministic fixture tests; rendered interaction still needs a client smoke test. No full game test suite is built in. |
| AI-agent ergonomics | Multi-language native build, generated code and hardcoded demo seams increase edit and feedback cost. | Text scene/resource files and GDScript offer smaller edits and fast headless runs; visual scene conflicts and generated UIDs still require discipline. |
| Maintainability | Reusing specialist code could pay off if gameplay catches up; maintaining a private gameplay fork is a high long-term burden. GPLv3+ engine terms matter. | Mainstream editor and simpler local project ownership; custom RTS systems become our maintenance responsibility. [MIT engine license](https://godotengine.org/license/) leaves project licensing flexible. |

## Architecture implications

Choose **Godot for presentation and tools plus a standalone simulation boundary**, initially written in GDScript with no physics-derived outcomes. Use data-driven definitions for factions, units, structures, resources and technologies. Commands cross a single input boundary and simulation emits state snapshots/events for rendering. This lets AI agents change content and mechanics in small files and test rules without a full graphics session. A C++/GDExtension simulation is a later option only if profiling demands it.

For multiplayer, start with a server-authoritative model in design, while the first prototype runs locally through the same command interface. Stable tick IDs, entity IDs, content version, RNG seed and state checksums should be part of the simulation API. This is an architectural precaution, **not a claim that multiplayer or cross-platform determinism already works**. Avoid choosing lockstep until repeatability is demonstrated across target platforms.

For the agreed launch funnel, a future authoritative match service must emit the eligible `match_started` and `match_completed` events defined in [North Star](../Roadmap/00-strategy/north-star.md). The worker prototype has no eligible match and must not be reported as a launched or completed match. The 15% later-day target remains provisional with no observed baseline.

## Decision pressure and open questions

Godot has the fastest credible route to testing whether the game loop is fun, but it provides no ready AoE2 depth. The largest unknowns are target unit counts, map sizes, client platforms, art approach, mod trust model, and multiplayer latency/authority requirements. Measure path query cost and frame time at representative unit counts before committing to a final navigation strategy. See [prototype plan](prototype-plan.md) and [ADR 001](architecture-decisions/001-engine-selection.md).
